# Phase 5: controlled department intelligence

`knowledge-base/` stores structured, scoped, sourced knowledge. At project time, `engine/knowledge/index.mjs` selects only relevant domain packs, retrieves **approved** historical items, ranks by topic/recency/confidence and writes `knowledge-context.json`. Domain-pack files are tagged `candidate_method`, so they frame analysis questions but are **not** evidence for current vendor specifications. The profile is also a candidate and cannot override corporate design, Evidence, or QA rules. There is no vector database and no automatic external upload.

`domain-packs/` references skills, knowledge, ontology, glossary and QA rules. First packs: TV Picture Quality, AI TV, Product Management. Twenty-one domain Skill files exist; only four with basic scope/dimension tests are enabled, the rest remain disabled pending substantive evaluation. `skills/custom/` contains narrow domain skills, while `./CPGHBPPT skill create <id>` scaffolds a disabled draft for review and test. Skill manifests carry version/enabled/deprecated; projects snapshot selected versions.

Review: `./CPGHBPPT review file.pptx` inspects read-only slide XML text and emits limited critic output under `feedback/reviews/`; external-source validity and visuals are **unassessed**. `./CPGHBPPT learn file.pptx` extracts a structural candidate, without copying a slide, into `knowledge-base/candidates/`. Explicit human review is required before `./CPGHBPPT knowledge promote <id> --confirm --reviewer ... --reason ... --scope ...`; approval means reusable structure only, not endorsement of historical claims. Rejected candidates remain in an audit trail but are not retrieved. No specific department decision was imported without an approved source.

Feedback: `./CPGHBPPT feedback diff <project-id> <edited-slide-specs.json>` records title/layout/deletion signals as `UNCLASSIFIED` in a local JSONL file. Only a person can classify why a change happened using `feedback confirm`; no single signal changes a profile. Stable preferences from at least three distinct confirmed projects are **suggestions**, not automatic policy updates. `./CPGHBPPT knowledge health` lists approved, stale and duplicate items; semantic contradictions require human review. Local dashboard counts are for system improvement, never employee scoring.

The quality rubric is in `docs/quality-rubric.md`. `engine/critic/` separates Content, Evidence, Product Logic, Storyline and Visual checks. A successful render QA is not a claim of business truth. The current screenshot Vision Critic remains optional/unavailable on this machine. A/B tests measure domain routing and scope coverage, not a proven improvement in executive effectiveness.

`./CPGHBPPT knowledge ingest <file>` can extract structural metadata from PPTX, PDF (text layer), DOCX, XLSX, CSV, Markdown and TXT. It deliberately does not persist the source text as permanent knowledge. DOCX/XLSX parsing reads basic OOXML text/cells only: scanned pages, equations, spreadsheet formulas, charts and embedded media are not semantically interpreted. The generated method-metadata candidate **cannot** be promoted directly; a person must write and source a substantive knowledge item. For actual historical decisions, use `./CPGHBPPT knowledge decision add` with source file, decision date, scope, reviewer, reason and explicit confirmation. A historical decision is still not a current fact.

Knowledge freshness: explicit `valid_until` takes precedence; tagged price, product-spec/AI capability and market-share items get 1/30/365-day review windows respectively. Other methods/decisions are not automatically expired, but must be checked for scope. Retrieval is token/metadata based, not semantic vector search. English/Chinese terminology suggestions live in `knowledge-base/glossary/`; they do not automatically translate a deck.
